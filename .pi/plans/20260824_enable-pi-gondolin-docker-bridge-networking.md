# Enable bridge networking in the Pi Gondolin VM

## Context

The Pi guest Docker daemon was explicitly started with its bridge device,
iptables programming, IP forwarding, and masquerading disabled. The Docker CLI
wrapper also forced every `docker run` into host-network mode. This prevents
standard Docker builds and Compose networks, including the Visonic development
stack.

The VM must keep its guest-local Docker data and never expose the host Docker
socket/settings. It must regain normal Docker bridge behavior rather than
working around the limitation in Visonic Compose files.

## Approach

1. Remove the Docker daemon network-disable flags and host-network CLI
   injection. Keep the guest CA propagation wrapper and `vfs` storage.
   **Check:** a fresh VM has Docker's default `bridge` network and can create a
   user-defined bridge network.
2. Provide the required `~/local_cache` directory to the guest at
   `/root/local_cache`, the Docker Compose expansion of `~/local_cache` for the
   guest root user. Preserve project-local `.gcloud/adc.json` through the
   workspace mount and forward its workspace-contained environment path.
   **Check:** policy tests assert the local-cache mount and sandbox environment
   tests cover the credential path allowlist.
3. Update the native canary and operator contract to require Docker-default
   networking: bridge inspection, bridge creation/removal, default-network DNS
   and HTTPS, a normal BuildKit build, and Compose default networking.
   **Check:** focused unit tests and the native canary pass with a rebuilt VM.
